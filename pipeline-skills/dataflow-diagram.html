Operational Dataflow Specification

Software-Change Workflow

Reference Intake → (Evidence Extraction ⇄ Evidence Review, reused) → Target Model Proposal → File Surface Discovery → Change Planning → Implementation → Validation → Fault Localization on failure.

Processes10 distinct
ReusableEvidence Extraction ×4, Evidence Review ×5
Loop-backValidation → Fault Localization → Confirmed Fault Set → re-invoke + cascade
OrchestrationUser-invoked, manual (Reference Intake may self-invoke Model Dataflow Specification)

Diagram

A sequence diagram instead of a flowchart: each column is a lifeline (the user, a process, or the Evidence Set store), and time runs top to bottom, so the invocation order — the thing this specifier actually cares about — is legible without edges converging on shared nodes. Solid arrows are invocations; dashed arrows are returns/outputs. The tinted rect block is the Evidence Cycle (Evidence Extraction → Evidence Review), called out once in full, then referenced by a Note at each later reuse point rather than re-expanded — it is the same reusable process every time (Rule 7). loop means "repeat until the stated condition holds"; opt is a single conditional branch; alt/else is a genuine fork. Evidence Review's second contract — reading a Fault Assessment instead of the Evidence Set, per Rule 8 — appears inside the fail branch at the bottom.

"Re-invoke fix point" targets whichever process originally produced the confirmed-wrong artifact — Target Model Proposal, File Surface Discovery, Change Planning, or Implementation — not always Target Model Proposal as drawn; the arrow is illustrative of the mechanism, not a fixed destination.

Legend

  • Lifeline (column) — the user, an invoked process, or the Evidence Set store; time runs top to bottom.
  • Solid arrow ( →) — an invocation, carrying its stated input.
  • Dashed arrow ( -->) — a return: an output or produced artifact.
  • Tinted rect — the Evidence Cycle (Evidence Extraction → Evidence Review); shown in full once, then referenced by Note at each reuse point, per Rule 7.
  • loop — repeat until the stated condition holds (e.g. no pending items remain).
  • opt — a single conditional branch (may or may not happen).
  • alt / else — a genuine fork, such as Validation's pass/fail.

Unresolved Dataflow Ambiguities

  1. Current Model creation source.When Reference Intake creates a Current Model rather than reviewing a supplied one, what does it read to do so? The codebase is the obvious candidate but is never named as an input.Resolved — Reference Intake reads the Change Request. If the user has no Current Model / dataflow reference on hand for the affected area, Reference Intake itself invokes Model Dataflow Specification against the existing codebase to derive one, rather than reading the codebase through some unnamed ad hoc process. The resulting Current Model is then treated as a normal Reference Intake output.
  2. Reviewed Evidence composition.Is it the full Evidence Set with decisions attached, or only the subset a decision touched? This decides what reaches Target Model Proposal.Resolved — There is no separate "Reviewed Evidence" artifact. Evidence Review is an iterative loop against the Evidence Set itself: a reviewing agent scans it and writes needs_review entries ({evIds, justification}) for anything ambiguous or conflicting, auto-stamped status: pending by the process, not the agent. The user is then presented each pending entry one at a time (a pure-skill exchange for now, no script) and resolves it per evId — an entry can bundle several evIds, but each gets its own status (outdated / invalid / to_delete / verified) and a mandatory justification, written back onto that evidence in place. to_delete evidence is archived and removed from the index; outdated/invalid evidence stays in the index, flagged. Evidence the agent never flagged is implicitly verified by default. The loop (scan → present pending → capture resolutions) repeats until no pending items or conflicts remain. Downstream consumers — starting with Target Model Proposal — read the Evidence Set directly and are individually responsible for programmatically excluding entries by status (e.g. skipping outdated/invalid) rather than receiving a pre-filtered artifact.
  3. Missing approval boundary before File Evidence Extraction / Change Planning.No interactive checkpoint is named for File Impact, yet Implementation later requires an "approved" plan.Resolved — The checkpoint is another invocation of the same reusable Evidence Review process (per Rule 7), not a new process. Generalizing: every Evidence Extraction invocation (References, Target Model, File Impact, Change Plan) is followed by an Evidence Review pass before the next process reads the Evidence Set — so File Impact evidence gets reviewed before Change Planning consumes it, the same way initial Reference evidence does before Target Model Proposal. Each Evidence Review invocation scopes itself by filtering the Evidence Set down to statusless entries (no status field yet) rather than maintaining a separate reviewed/unreviewed location — entries already carrying a status from a prior pass (verified/outdated/invalid/to_delete) are skipped automatically, consistent with the status-filtering scheme downstream consumers already use.
  4. Change Plan approval, specifically.Step 8 (Change Planning) names no interactive exchange, but Step 10 (Implementation) requires the plan already be approved.Resolved — There is no separate granular approval of the Change Plan (or File Impact) document. The one interactive approval gate is upstream, at Target Model Proposal: once the user approves the holistic architectural design, File Surface Discovery → Change Planning → Implementation proceed programmatically without further plan-level sign-off. The real backstop is downstream instead: Validation against the build (manual, initially) is the de facto approval gate. A validation failure is the trigger that initiates a search back up the causal chain — Implementation → Change Plan → File Surface → Target Model, potentially as far as the dataflow model description or the original requirement itself.
  5. Validation failure routing."Invoke the appropriate upstream skill" implies a decision with a bounded domain — is that domain always {Target Model Proposal, Change Planning, File Surface Discovery, Implementation}, or can a trace also implicate Reference Intake or Evidence Review?Resolved — Not an unbounded routing decision — an explicit new process, Fault Localization, triggered by a failing Validation Result. It reads the Bug Report(s) Validation produced plus every artifact in the upward chain (Candidate Implementation, Change Plan, File Impact, Target Model, the Evidence Set), and non-destructively marks suspect artifacts — annotated, nothing deleted — writing a disk-persisted Fault Assessment: {artifact ref, suspect status, justification, [bug report ids implicated]}. The Evidence Review pattern (same pending → one-at-a-time presentation → mandatory-justification resolution loop from ambiguity 2) is reused against the Fault Assessment rather than the Evidence Set, producing a Confirmed Fault Set mapping each user-confirmed-wrong artifact to the bug report(s) that implicated it. To close the loop: each confirmed-wrong artifact's current version is marked superseded (archived, not deleted) and the process that originally produced it is re-invoked with the Confirmed Fault Set entry as extra input; that regeneration then cascades forward through the normal dataflow — every process between the fix point and Implementation re-runs in sequence — ending at a new Candidate Implementation that returns to Validation.
  6. Evidence Set staleness on re-entry.After a loop-back, are previously derived Target Model / File / Plan Evidence regenerated, patched, or left as-is beside the new Validation Result evidence?Resolved — Not left ambiguously as-is. Under the Fault Localization / Confirmed Fault Set mechanism above, a loop-back explicitly supersedes (archives, doesn't delete) the confirmed-wrong artifact and everything derived from it, then regenerates them via the forward-cascade re-invocation. Staleness is resolved by the same non-destructive mark-and-regenerate pattern used everywhere else in the workflow, not by a separate rule.
